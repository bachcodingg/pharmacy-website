TASK 1 - VALIDATE THE CORRECTOR CHANGE  (HIGHEST PRIORITY, UNFINISHED)
--------------------------------------------------------------------------------
WHAT WAS DONE
app/corrector.py `_fuzzy_lookup` was scanning every vocabulary form in the +/-2
length buckets across two views, running an O(n*m) edit-distance DP on each.
That is audit finding F-08 (search p95 far over its 50ms budget).

A character-signature prune was added. `char_signature()` builds a bitmask of
which characters a string contains, and the scan now skips any form whose
signature differs from the query's by more character classes than the distance
cap could possibly cover - two integer operations instead of a DP table.

THE SUBTLE PART - DO NOT "SIMPLIFY" THIS
The bound is scaled by SUB_COST_ADJACENT (0.5):

    edit_distance(a,b) >= popcount(sig(a) & ~sig(b)) * SUB_COST_ADJACENT

Dropping that factor looks like a tighter, cleaner bound. It is simply false.
Keyboard-adjacent substitutions cost 0.5 each, so two of them change two
character classes for a total distance of only 1.0. I made exactly this mistake
mid-session and measured the damage: held-out top-1 fell from 0.930 to 0.926 -
it silently loses the very typos this corrector exists to catch. The scaled
(correct) version is what is in the tree now. Leave the factor alone.

MEASUREMENTS SO FAR (all on this machine; the PDF's numbers came from another
machine, so compare against these, not against the PDF)

    original code           p95 1349 ms   (999-query harness)
    unscaled/wrong bound    p95 1.55 ms   but top-1 0.926  <- LOST ACCURACY
    scaled/correct bound    ~128 ms for "etrogen" (single-query spot check)
                            ACCURACY NOT YET MEASURED      <- this is the gap

    baseline accuracy to match:
        top1_accuracy 0.930   top3_recall 0.938   no_candidates_rate 0.040

WHAT YOU MUST DO

1a. Run the held-out harness and compare against that baseline. It takes
    several minutes - run it in the background and wait for the completion
    notification rather than polling it.

        cd /d/fpt/pharmacy-search/backend
        python eval/held_out.py

    PASS CRITERIA: top1_accuracy >= 0.930 AND no_candidates_rate <= 0.040,

    Fastest way to isolate a regression: temporarily set

    return to baseline.

1b. Run the full latency harness for a real p95:

    Record the number. Expect roughly 100-150 ms p95 - about 10x better than

TASK 2 - FINISH F-08 PROPERLY  (optional; the interesting one)
--------------------------------------------------------------------------------
Only after Task 1 passes. Going from ~128 ms to under the 50 ms budget needs
real candidate generation, not just a better filter. The audit suggests a
SymSpell deletion index or a BK-tree.

Recommended: SymSpell-style deletion neighbourhood.
  - In Corrector.__init__, for each form in the telex and no-accent views,
    generate every string obtainable by deleting up to 2 characters, and map
    each to the forms that produced it.
  - At query time, do the same for the token and look up the union.
  - Run the real edit_distance only on that shortlist.

RISK AND HOW TO HANDLE IT: MAX_EDIT_DIST is 3, so a depth-2 deletion index can
miss distance-3 candidates and WILL cost recall. Measure it. If top-1 drops
below 0.930, either raise the deletion depth (memory cost) or keep the
signature prune as a fallback full scan for tokens that find nothing.

Whatever you try, re-run eval/held_out.py every single time and treat 0.930
top-1 as a hard floor. Accuracy is the product here; latency is second.

Cheaper and also worth doing: an LRU cache on Corrector.correct(). The index is
immutable at runtime, so there is nothing to invalidate. It will not move the
benchmark (999 distinct queries) but real traffic repeats heavily.

GOTCHAS - THINGS THAT WILL BITE YOU
--------------------------------------------------------------------------------
* tests/conftest.py sets PHARMACY_RATE_LIMIT_ENABLED=0, because the suite
  registers dozens of accounts from one client and would otherwise trip its own
  limiter. tests/test_ratelimit.py re-enables it with a monkeypatch fixture. If
  you add a test that needs limiting on, copy that fixture pattern.

* conftest also redirects PHARMACY_DATA_DIR, PHARMACY_SEARCH_DB,
  PHARMACY_LOG_DIR and PHARMACY_LEARNING_DIR into a temp directory. Never point
  tests at backend/data.

* tests/test_checkout.py::_in_stock_product deliberately filters to
  NON-prescription products. If you "simplify" that filter away, every checkout
  test breaks, because Rx items now go to awaiting_prescription instead of
  placed. There is a _prescription_product helper right next to it.

* PHARMACY_EXPOSE_RESET_TOKEN puts the reset token back into the HTTP response.
  It defaults OFF and must NEVER be set in a deployed environment. Tests read
  the token from the database instead - see _reset_token_from_db in
  tests/test_auth.py.

* Schema changes go in db.py MIGRATIONS as a new numbered entry. Do NOT rely on
  adding a column to the CREATE TABLE in SCHEMA: that only affects databases
  created afterwards, which is exactly the drift the migration table exists to
  prevent. I made that mistake once this session (a UNIQUE constraint on
  reviews) and fixed it by moving it to a CREATE UNIQUE INDEX in INDEXES.

* SEARCH_TEXT_FOLD_VERSION in db.py must be bumped whenever search_key()
  changes how names are folded, or existing rows keep a stale search_text.

* Local state moved. backend/logs/ and backend/learning/*.json now live under
  backend/data/logs/ and backend/data/learning/. The existing files were moved
  there during the session, not deleted.

* eval/held_out.py and eval/latency.py construct Corrector() directly rather
  than through get_corrector(), so they are unaffected by the config path
  changes. That is also why they are a clean measurement of corrector changes.

* The eval harness is slow (several minutes). Run it in the background and wait
  for the completion notification instead of polling it.
